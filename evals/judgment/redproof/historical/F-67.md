**Q1 · Which Makefile**
- (a) Upgrade `dlh-api/console/Makefile` in place — same three target names, and delete the empty `dlh-api/Makefile` placeholder ← ✅ recommended
- (b) Create a new `dlh-api/Makefile` that drives console via `-pl console`, and retire the console one

*Every path in the tooling (`CHANGES_DIR`, `changeLogFile: ./src/main/resources/...`, the `liquibase` profile) is console-relative and console-scoped, so the Makefile belongs next to the module it migrates; the root placeholder is dead weight.*

**Q2 · Numbered output**
- (a) `make makemigration name=add_foo` writes the diff **straight into** `db/changelog/changes/NNNN_add_foo.yaml`, auto-picking the next number ← ✅ recommended
- (b) Keep the scratch dump + the human copy-paste step, and let this issue only tidy the wrapper

*(a) is the entire delta between the issue's reference file and what's on disk — it removes the one manual step that can silently produce a mis-numbered or forgotten file. Requiring `name=` mirrors Django's `--name` and keeps filenames greppable; without it we'd get `0003_auto_20260814.yaml`.*

**Q3 · Generated metadata**
- (a) Treat the generated file as a **draft**: `makemigration` writes it, the dev hand-edits the changeset `id`/`author` (and adds `rollback:`) before committing — help text says so ← ✅ recommended
- (b) Commit exactly what `liquibase:diff` emits, no hand-editing expected

<details><summary>Background</summary>

The changelog has both conventions in it. Diff-generated entries look like `id: 1776680168450_add_user_id`, `author: pwliangc (generated)`. Everything hand-written recently looks like `id: 20260813_create-user-workspace-memberships-table`, `author: paul-lin`, and several carry explicit `rollback:` blocks. `liquibase:diff` never emits a `rollback:` block, and its epoch-millis ids sort unpredictably against the dated ones if anyone ever reads the file chronologically.
</details>

*A changeset id is permanent — it's the applied-migration identity in `databasechangelog` — so it's worth 10 seconds of human naming; and diff output routinely includes drift you did not intend, which a review-before-commit step catches.*

**Q4 · Tag per migration**
- (a) Drop the auto-appended `tagDatabase` changeset from the reference ← ✅ recommended
- (b) Keep it — every generated migration ends with a tag, enabling `rollbackToTag`

*The tag only pays off with a `make rollback`, which isn't in the reference and which would fail anyway on the changesets that lack `rollback:` blocks. Adding a tag row per migration now, for a command that doesn't exist, is ceremony we'd have to keep forever. Easy to add later alongside a real rollback target — say (b) if you want that path opened now.*

**Q5 · Scope and track**
- (a) `track: fast` — migrations only (the three targets + `help`), local developer loop only ← ✅ recommended
- (b) `track: spec` — treat it as "daily operation" broadly: also `build` / `test` / `run` / `docker up` targets, and settle how migrations reach CI/production

*Once Q1–Q4 are answered this is roughly 40 lines of Make with no user-facing behavior and no JUnit acceptance surface (the configured `acceptance_test` runs `mvnw -pl console test`, which can't black-box a Makefile) — verification is "run the three targets against local docker-compose". Pick (b) if you want the EM seat to also rule on the production migration path, which is genuinely unsettled given `spring.liquibase.enabled: false` means nothing migrates prod automatically today — but that's a separate story and I'd file it as its own issue.*
