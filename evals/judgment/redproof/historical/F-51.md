## Intake summary — issue #51

The idea as filed is a full SQL-workbench backend: query execution, schema browsing, history, lint, complexity, EXPLAIN, and cluster load. That is several distinct stories. Per one-issue-one-story, this issue keeps the smallest core that delivers the benefit — **running a SQL query against Trino from ADMC** — and the rest become sibling issues (story blocks below).

### User story (this issue)

As a **Lakehouse Console admin**, I want to **submit a SQL query to a Trino cluster from ADMC and follow it through to completion — see its status, page through its results, or cancel it**, so that **I can investigate lakehouse data without leaving the admin portal or shelling into Trino directly**.

### Acceptance criteria

- [ ] An admin can see the list of Trino connections they are allowed to use; connections they are not allowed to use are not offered and cannot be targeted.
- [ ] An admin can submit a SQL statement against an allowed connection and receive a query handle immediately (submission does not block on query completion).
- [ ] Polling the handle reflects the query's real lifecycle (queued / running / finished / failed), including Trino-side failure detail on failure.
- [ ] Finished results are retrievable in pages of a requested size; results beyond the configured row cap are truncated with an explicit "truncated" indication, never an error or an unbounded payload.
- [ ] Cancelling a running query actually stops it on the Trino side (observable as user-cancelled in Trino), not merely in ADMC's records.
- [ ] A user who is not on a connection's allow-list is rejected on submit with a clear error.
- [ ] Connection credentials never appear in any response, error message, or log output.
- [ ] Every submitted query is recorded in an audit trail attributing the query text, target connection, and requesting user.
- [ ] All endpoints follow ADMC's standard response envelope and error-code conventions.

### Context

ADMC is the lakehouse admin portal; today admins leave it to run ad-hoc SQL. A sibling project (LH-PRISM) already built and locally verified this exact backend against Trino — it serves as a de-risked reference and a hard-won caveat list (the issue body carries ten guardrails: result-size buffering traps, TLS-only auth with credential redaction, cancel-must-reach-Trino, dedicated audit channel, and more). The ask is a **native re-implementation following ADMC's own conventions**, not a code port. The frontend is a separate later effort; this story is done when a frontend could be built against the documented contract. The author has already ruled: the query path gets its own purpose-built async model rather than ADMC's generic 3-state job queue, auth is BASIC+TLS only, and access control is config allow-lists (OPA deferred).

### Proposed track

`track: spec` — user-facing behaviour, a new domain model, and real contract decisions (states, paging, error shapes) that two engineers would build differently.

### Out-of-scope siblings (file separately)

1. **Schema browse** — As an admin, I want to browse catalogs/schemas/tables/columns of a connection, so that I can write queries without memorizing the lakehouse layout.
2. **Query history** — As an admin, I want to see my past queries and their outcomes, so that I can re-run and reference earlier work. (Audit *recording* is in the core story; the browsable history endpoint is this sibling.)
3. **Pre-run SQL feedback** — As an admin, I want fast lint, complexity estimation, and EXPLAIN on a draft query, so that I catch mistakes and expensive queries before running them.
4. **Cluster load view** — As an admin, I want to see current Trino cluster load, so that I can time heavy queries.

Also out of scope per the author: frontend, MCP/agent path, Doris connector, advanced auth (Kerberos/OAuth2/mTLS), SIEM audit forwarding.

### Decision trail

- **TaikerLiang (author, gate holder)** filed the full brief and settled: native ADMC re-implementation with LH-PRISM as reference only; dedicated async-query model instead of the generic task queue; BASIC+TLS auth only, insecure-over-HTTP never enabled; RBAC via config allow-lists with OPA deferred; the ten guardrails and the non-goals list.
- No other participants; no discussion comments before the summary request.

### Assumptions (unanswered → resolved to my recommendation)

1. **Scope** — Shrunk to the core query path (connections + submit/status/results/cancel). The other six capabilities in the original table are siblings, listed above. *Why: each is independently shippable; the query path alone delivers the stated benefit.*
2. **Read-only vs write** — v1 accepts read-style statements only (SELECT/SHOW/DESCRIBE/EXPLAIN); DML/DDL is rejected with a clear error. Writes, if ever wanted, are a future sibling. *Why: an admin portal executing arbitrary writes against prod lakehouse data is a blast-radius decision the human should make explicitly, not inherit silently.*
3. **Single vs multiple targets** — v1 supports multiple config-defined connections, each with its own allow-list (dev/qa/prod clusters differ, and the connections endpoint exists precisely for this). *Why: a single-target contract would visibly break the moment a second cluster is added.*
4. **Audience** — Existing ADMC admin users only; no new user class, same authentication as the rest of the portal.
5. **Audit** — Audit recording of every execution is inside the core story (it is a guardrail, not a feature); the browsable history UI endpoint is sibling #2.
6. **Guardrails** — The ten lessons in the issue body are treated as spec-stage input (constraints the spec must honor), not intake-level acceptance items, except where they are user-observable (cancel semantics, credential redaction, row caps — already in the criteria above).
