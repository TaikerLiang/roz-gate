**[product] · Q1 · one record per person (story-level)**

When a username holds authorization mappings in three workspaces, should the
console still show one user record carrying three workspaces, or three
separate user records?

- (a) One user record per person, with workspace membership held as its own
  set of username-and-workspace pairs ← ✅ recommended
- (b) One user record per username-and-workspace pair, so `users.username` is
  no longer unique

*Option (b) makes the same person appear three times in the admin console user
list, splits their `enabled` and super-admin flags across rows that can
disagree, collides with the existing unique constraints on `username`, `email`
and `user_id`, and breaks the single-record lookup that login's lazy
provisioning depends on (`findByUsername` returns an `Optional`, so a second
row makes login throw) — while option (a) satisfies every acceptance line
exactly as written, including "represented once per workspace" and "a pair can
exist only once".*

*If your decision changes the user story, I will mirror a note to issue #63.*

--- [thread-post-inline] ---
**[em] · Q2 · department-granted membership (story-level)**

Workspace access is granted by **two** authorization tables — the username
mappings this story copies, and `console_opa_deptid_roles`, which grants access
by department (PK `deptid` + `workspace`), with every user record carrying a
`dept_id`; should a user whose only access comes from their department also
end up carrying that workspace?

- (a) No — copy the username mappings only, exactly as the issue names them;
  department-granted access is a separate question that #61 inherits
  ← ✅ recommended
- (b) Yes — also derive membership by joining `users.dept_id` to the deptid
  mappings (needs its own detail: whether a dept-derived membership is
  distinguishable from a username-derived one, and what happens when both
  grant the same pair)

*The acceptance criteria are written entirely in terms of usernames, so (a)
satisfies them literally and keeps the one-time job small — but the user story
promises "the console can tell which workspace a user belongs to", and under
(a) a user who reaches a workspace purely through their department will carry
no workspace at all, which is a wrong answer rather than a missing one. The
holder should decide whether that gap is acceptable for the duration of the
chain, since #54 is what will eventually read this.*

*If your decision changes the user story, I will mirror a note to issue #63.*

**[em] · Q3 · which mappings count (story-level)**

Does **every** mapping row count as membership regardless of its `role` value,
including `VIEWER` (0) and `DEFAULT` (-1)?

- (a) Yes — any mapping row means membership; the role value is authorization's
  business and this job does not interpret it ← ✅ recommended
- (b) No — only roles at or above some floor count as membership (needs the
  floor named, e.g. exclude `DEFAULT`, or exclude both `DEFAULT` and `VIEWER`)

*`ConsoleAuthRoleEnum` defines `DEFAULT(-1)`, `VIEWER(0)`, `EDITOR(1)`,
`ADMIN(2)`, `SUPERADMIN(99)`, and the acceptance criteria say "every username
that has authorization role mappings" — so (a) is what the story asks for and
keeps the job free of any authorization policy of its own. But (b) is worth a
deliberate refusal rather than an accident: if `DEFAULT` is in practice a
placeholder meaning "no explicit grant", (a) records a membership for someone
who has no real access, and this job's output is what #54 will eventually show
users.*

*If your decision changes the user story, I will mirror a note to issue #63.*

**[product] · Q4 · where counts appear**

Must the copied and skipped counts be readable in the HTTP response when the
job is triggered through the existing
`POST /api/v1/admin-console/cli/job/{name}` endpoint, or is the job log the
single place they appear?

- (a) Job log only; the HTTP endpoint keeps returning its generic success body
  ← ✅ recommended
- (b) Both — the counts also come back in the HTTP response body

*Every CLI command is auto-exposed on that endpoint and it returns a fixed
"Command executed successfully" message for all of them, so (b) means
reshaping the shared CLI job contract for the sake of one one-time job; the
operator running a migration will be reading the log regardless.*

**[implementer] · Q5 · which trigger surface**

The HTTP trigger gives up after `command-timeout-seconds` (default 180) but
cannot actually interrupt the running job, so a long migration returns HTTP 400
"Command timed out" to the operator and then logs its success summary minutes
later — should the production migration therefore be run only through the
startup-argument surface?

- (a) Yes — `--command=workspace-membership-backfill` is the surface for the
  real migration, and the HTTP trigger stays for small data and tests
  ← ✅ recommended
- (b) No — raise `command-timeout-seconds` for the migration window and run the
  real migration over HTTP as well

*This is a "failed run that actually succeeded" trap: the one signal that is
supposed to separate failure from a run that copied nothing (**R8**, **S18**)
becomes unreliable over HTTP the moment the run outlives the timeout. Option
(a) costs a line of runbook and nothing else; (b) needs a number, which needs
**Q6**. Making the endpoint fire-and-forget would fix it properly but reshapes
the shared CLI job contract for one one-time job, which the out-of-scope list
already rules out.*

--- [thread-post-inline] ---
**[implementer] · Q6 · migration data volume**

Nobody has stated how many rows `console_opa_username_roles` and `users`
actually hold in production — should that be measured before the migration
window, or does the job ship on the assumption that the data is small?

- (a) Measure first — the row counts are one query, and they decide **Q5**'s
  answer and whether a maintenance window is needed ← ✅ recommended
- (b) Ship on the assumption that the data is small and find out at run time;
  the job is re-runnable, so an interrupted first attempt is recoverable

*The job is correct at any size — it copies in bounded batches and re-running
is the defined remedy (**R6**, **R15**) — so this is not a correctness
question, it is an operations one. But every runtime statement anyone makes
today is a guess: the only concrete numbers in the repo are the ten seed
mapping rows, which tell us nothing about production.*

--- [thread-post-inline] ---
**[implementer] · Q7 · username collation**

**R11** defers "same username" to the database's own equality, which assumes
`users.username` and `console_opa_username_roles.username` carry the same
collation — should that be verified in production before the migration window,
or is failing loudly at run time good enough?

- (a) Verify beforehand — one query against `information_schema`, run before
  the window rather than during it ← ✅ recommended
- (b) Rely on the loud failure — if the collations differ, MariaDB raises error
  1267 on the join and the run fails with no summary line, which is the
  correct behaviour anyway

*Both options are safe: a collation mismatch can never cause a silent wrong
match, only a hard failure. The difference is purely when the operator finds
out. A schema built from `db/changelog.yaml` with defaults has one uniform
collation, so (b) is very likely fine — but "very likely" is doing real work in
that sentence for a deployment nobody has inspected.*

--- [thread-post-inline] ---
**[implementer] · Q8 · ghost skip list**

Ghost usernames currently survive a run only as log lines — does anything need
to work through them systematically afterwards, or is the log the whole
requirement?

- (a) Log lines only, exactly as the acceptance criteria state ← ✅ recommended
- (b) Also persist the skipped usernames as data, so #61 or the operator can
  query them instead of grepping a log

*The acceptance criteria ask for names in the log and nothing more, and (b)
means a second table with its own lifecycle question (when is a skip entry
cleared — when the user record finally appears, or never?) for a story whose
whole point is unblocking the chain. Worth a deliberate refusal rather than an
accident, though, since the operator's stated next action after a skip is to go
look at that username.*
